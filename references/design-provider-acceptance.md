# Design Provider QA — separate style conformance from product UX

## Before calling a Provider

- Confirm independent original SKILL.md actually installed/read; provider mode and compatible framework/surface declared.
- Inspect accepted DESIGN.md and user-specified style; preserve existing visual conventions for routine optimizations.
- Handoff includes business task, IA, behaviors, state requirements, permission/API contracts, technical stack.
- Do not grant source-edit permission during style-candidate/spec/style-audit.
- Provider recommendation does not grant permission to install frameworks, dependencies or third-party Skills.

## After Provider work

- Check requested style/preset is actually compatible with the project's framework and accepted brand constraints.
- Check focus, keyboard navigation, errors/loading, long CJK text, zoom, responsive layout and reduced-motion.
- For motion, repeated rapid toggles/open-close, interruption, focus restoration and truthful state updates.
- Review genuine rendered screen; static screenshot does not prove interaction correctness.
- Check component mapping retains required product information and density rather than copying vendor demo layouts.
- Record style-conformance separately from Hallmark read-only audit and Impeccable critique/audit.
- Keep one project-owned DESIGN.md, update only when acceptance/checkpoints permit.
- Track status executed / skipped-not-needed / unavailable / blocked / failed and evidence. No hypothetical QA passed.

No provider? Product-ui still executes its normal general UX and browser QA with an explicit no-provider status.
