# Product Type Routing

Use product type to choose interaction patterns, not merely visual style.

## ToB operational systems
Examples: CRM, ERP, finance ops, document processing, support console, data admin.

Default traits:
- repeated daily use
- many records
- high information density
- comparison and batch work
- permissions, ownership, statuses, timestamps
- keyboard and shortcut value may be high

Prefer:
- sidebar or stable global navigation
- table/list-first record surfaces
- persistent search/filter/sort
- compact forms
- visible status and next action
- detail drawer when it preserves context

## ToB analytical systems
Examples: BI, monitoring, portfolio analytics, usage analytics.

Prefer:
- questions and decisions first, charts second
- KPI only when the metric has a decision purpose
- visible time range and filter context
- trends, deltas, segmentation, anomaly evidence
- drill-down paths from summary to evidence

## ToC utility tools
Examples: watermark tool, converter, scanner, editor, calculator, small AI tool.

Prefer:
- one obvious primary job
- short path to first success
- low setup cost
- progressive disclosure for advanced options
- preview before irreversible export/apply actions

## ToC content/community products
Examples: feed, forum, voting, social contribution, discovery.

Prefer:
- clear content hierarchy
- obvious contribution/reaction model
- trust, moderation, identity, and reporting states
- predictable back/navigation behavior

## ToC mobile-first apps
Prefer:
- thumb-reachable primary actions
- single-column flow by default
- bottom navigation only for truly top-level destinations
- avoid desktop sidebar metaphors copied into mobile

## Mixed products
Many products have both analytical and operational surfaces.
Do not force one page pattern across all pages.
A dashboard may summarize; a workbench should optimize action throughput.
